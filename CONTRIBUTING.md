# Contributing

## Setup

Install the .NET SDK 10 (it builds the `net8.0` and `netstandard2.0`
library targets; `global.json` rolls forward from 8.0). The contract suite
also needs Node.js, for `npx`. Then:

```sh
dotnet restore
dotnet tool restore                                     # DocFX, pinned in .config/dotnet-tools.json
dotnet format --verify-no-changes                       # style and analyzers, examples included
dotnet run --project tools/Generator -- --check          # generated code and resource reference match the IR
dotnet build -c Release                                  # warnings are errors; builds examples/ too
dotnet test -c Release                                   # unit tests, doc samples and doc links
dotnet test tests/TeachMeHipaa.ContractTests -p:ContractTests=true   # Prism contract suite
dotnet docfx docs/docfx/docfx.json --warningsAsErrors    # the API reference, into docs/docfx/_site
dotnet pack src/TeachMeHipaa -c Release -o artifacts     # the .nupkg and .snupkg
```

Unit tests target `net10.0` locally. CI also runs them on `net8.0`, against
the library's `net8.0` build, by setting `CI=true`.

## Generated and hand-written code

The library is a hand-written core plus a service and model layer generated
from the vendored IR (ADR-0001).

| Path                                   | Origin                                                                      |
| -------------------------------------- | --------------------------------------------------------------------------- |
| `src/TeachMeHipaa/Core/`               | Hand-written: client, options, request pipeline, auth, webhooks, pagination |
| `src/TeachMeHipaa/Extensions/`         | Hand-written members added to generated types (see below)                   |
| `src/TeachMeHipaa/Models/`, `Services/` | Generated by `tools/Generator`; do not edit                                 |
| `docs/reference/resources.md`          | Generated by `tools/Generator`; do not edit                                 |
| `tools/Generator/`                     | The generator                                                               |
| `openapi/`, `OPENAPI_VERSION`          | Vendored from the monorepo; do not edit (see `openapi/README.md`)           |

Every generated file starts with a "Generated from openapi/sdk-ir.json by
tools/Generator. Do not edit." banner (an HTML comment in the Markdown
reference). To change generated code, change the
generator, or fix the IR upstream in the monorepo's `tooling/sdk-ir` and
re-vendor it.

The request pipeline is a chain of `DelegatingHandler`s built in
`TeachMeHipaaClient`: authentication (with the 401 replay), retries,
timeout, opt-in logging, then the transport (the shared pool, the caller's
`HttpClient` or `HttpMessageHandler`, or `AddTeachMeHipaa`'s factory
client). `ApiRequestor` binds the Organization, sets headers and maps
responses to models or exceptions.

A generated type that needs hand-written members is a `partial` class or
record: the generator lists it in `ExtendedServices`
(`tools/Generator/ServiceWriter.cs`) or `ExtendedModels`
(`tools/Generator/ModelWriter.cs`), and `src/TeachMeHipaa/Extensions/` adds
the members, such as `EventService.TailAsync` and `Operation.WaitAsync`. Add
a new hand-written method to `Extensions` in
`tests/TeachMeHipaa.Tests/GeneratedSurfaceTests.cs`. An extended service
also needs a line for the Markdown reference in `ExtensionDocs`
(`tools/Generator/ReferenceWriter.cs`), since the IR doesn't know its
hand-written methods; the generator refuses to run without one.

## Regenerating from a new IR

1. Rebuild the IR in the monorepo
   (`bun tooling/sdk-ir/bin.ts --spec <spec> --out <dir>`), copy
   `openapi.developer.json`, `sdk-ir.json` and `sdk-ir.schema.json` into
   `openapi/`, and put the IR's `source.release` in `OPENAPI_VERSION`.
2. Run `dotnet run --project tools/Generator`. It validates the IR against
   its schema, then rewrites `src/TeachMeHipaa/Models/` and
   `src/TeachMeHipaa/Services/` deterministically, deleting files the IR no
   longer produces, and `docs/reference/resources.md`. An IR shape it has no
   rule for stops it with an error rather than a guess.
3. Run `dotnet build` and `dotnet test`. `GeneratedSurfaceTests` fails if
   any spec operation lacks exactly one public method with the expected
   name; add new operations to its `ExpectedMethods`. The generator's
   `--check` (run in CI) fails if the committed output differs from what it
   writes.
4. Run the contract suite, add a call for any resource family it doesn't
   cover yet, and add a CHANGELOG entry.

## Tests

| Project                            | What it runs                                                                          | In `dotnet test`                     |
| ---------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------ |
| `tests/TeachMeHipaa.Tests`         | The public client with a fake transport, webhook vectors, generated coverage, DI      | Yes                                  |
| `tests/TeachMeHipaa.ReadmeTests`   | Every README and guide sample, compiled and run against the fake transport; doc links | Yes                                  |
| `tests/TeachMeHipaa.ContractTests` | The client against a Prism mock of `openapi/openapi.developer.json` (needs Node.js)   | No: `-p:ContractTests=true`          |
| `tests/TeachMeHipaa.SandboxTests`  | A read-only smoke test against the real Sandbox                                       | Yes, but skipped without credentials |

Unit tests cross only the seams agreed in the spec: the public client with
`Support/FakeHttpMessageHandler` as its `HttpMessageHandler` and a fake
`TimeProvider` (`Support/TestTime`), the pure webhook functions, and the
generated surface. Take expected values from the spec, the research docs or
worked examples, never from the code under test. No test calls the live API.

### Doc samples

Every ```` ```csharp ```` block in `README.md` and `docs/guides/*.md` must
follow a `<!-- sample: <id> -->` line, with ids unique across all of them.
Before compiling, the README test project runs
`Tasks/ExtractReadmeSamples.cs` (an MSBuild inline task) to write the
samples into `obj/ReadmeSamples.g.cs`: each block's statements become a
method, and the types it declares (after its statements, as in a top-level
program) go into the namespace. A sample that stops compiling fails the
build with an error at its line in the document.

To run against the fake transport, the extractor declares the variables a
sample uses without creating (`client`, `builder`, `app`, `accessToken`,
`signingSecrets`) from `ReadmeHarness`, and adds the fake as
`HttpMessageHandler` to each `TeachMeHipaaClientOptions` initializer
(except in samples using `AddTeachMeHipaa`, whose test configures the
factory client, and samples that bring their own `HttpMessageHandler` or
`HttpClient`). `ReadmeTests.cs` (README samples and those moved from it)
and `GuideSampleChecks.cs` script the fake, run each sample and check what
it printed and sent; the ASP.NET Core samples run in a `TestServer`. To add
a sample, tag it and add a check to `Checks`; the suite fails if a sample
has none. `dotnet format` doesn't see the Markdown, so keep sample code in
the repository's style by hand.

`DocLinkTests.cs` checks that every relative link in the README, the
guides, the docs index, the resource reference, this file and
`examples/README.md` points at a file that exists, and at a heading that
exists when it has an anchor (GitHub's anchor rules).

### Contract suite

```sh
dotnet test tests/TeachMeHipaa.ContractTests -p:ContractTests=true
```

The project sets `IsTestProject` only with `ContractTests=true`, so a plain
`dotnet test` builds it but never needs Node.js. A collection fixture,
`PrismMock`, starts `npx --yes @stoplight/prism-cli@5.16.0 mock
openapi/openapi.developer.json` on a free port, waits until Prism is
listening, and stops its process tree after the run. Prism serves the spec's
paths without `/v1`, so the client's `BaseUrl` is the bare host. The client
uses a `StaticTokenProvider` and an explicit `OrganizationId`, since Prism
can't mock the form-encoded token endpoint.

`ContractTests` makes one representative call per resource family. Prism
answers a request that breaks the spec with a 4xx, which fails the call, and
`ViolationRecorder` (a `DelegatingHandler`) collects the request violations
Prism names in its `sl-violations` header, failing the test if there are
any. A harness test checks that a deliberately invalid request is caught.

Prism serves static responses built from the spec's schemas. `--dynamic` and
`--errors` are off on purpose: Prism's own generated responses break the spec
(static strings ignore `pattern`; dynamic numbers break OpenAPI 3.1
`exclusiveMinimum`), so either flag makes valid SDK requests fail. Response
violations are therefore ignored; the suite still checks that each response
reads into its typed model.

### Sandbox smoke test

```sh
TMH_SANDBOX_CLIENT_ID=cli_… TMH_SANDBOX_CLIENT_SECRET=tmh_cs_… dotnet test tests/TeachMeHipaa.SandboxTests
```

It introspects the token (expecting `Mode` `test`), lists Courses and lists
Learners in the Sandbox Environment. It never writes. Without both variables
every test is skipped, and CI never sets them.

## Documentation

| Path                          | What it is                                       | Kept in sync by                                            |
| ----------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| `README.md`                   | Overview, install, quickstart, links             | `tests/TeachMeHipaa.ReadmeTests` (samples, links)          |
| `docs/guides/*.md`            | Task guides for partner developers               | `tests/TeachMeHipaa.ReadmeTests` (samples, links)          |
| `docs/reference/resources.md` | Every service and method, from the IR            | `tools/Generator --check` (CI) and `GeneratedSurfaceTests` |
| XML docs, built with DocFX    | The API reference on GitHub Pages                | The Docs workflow fails on any DocFX warning               |
| `examples/*/`                 | Runnable programs against the Sandbox            | `dotnet build` and `dotnet format` (CI); not run           |
| `docs/README.md`              | Index of all of the above and the design records | `tests/TeachMeHipaa.ReadmeTests` (links)                   |

When you change behavior, update the guide that describes it and its
sample's check; when the IR changes, regenerate and commit the reference
with the code. The XML docs on public types are the API reference, so
write them for partner developers.

The API reference is a DocFX project in `docs/docfx/`. It reads the
library's `net8.0` build and writes the site to `docs/docfx/_site/`
(ignored by git, like the intermediate `docs/docfx/api/`):

```sh
dotnet tool restore
dotnet docfx docs/docfx/docfx.json --warningsAsErrors    # build
dotnet docfx docs/docfx/docfx.json --serve               # build and serve on http://localhost:8080
```

`--warningsAsErrors` turns DocFX's warnings, such as an unresolved `cref`
or `xref`, into failures, as in CI. The compiler already fails the build on
a public member without XML docs (`GenerateDocumentationFile` with warnings
as errors).

`.github/workflows/docs.yml` builds the reference on every push and pull
request and uploads it as a Pages artifact. On `main` it also deploys it
to GitHub Pages, at <https://teachmehipaa.github.io/teachmehipaa-dotnet/>.
**Pages must be enabled once** (Nick): in the repository's Settings >
Pages, set the source to "GitHub Actions". Until then the deploy job
fails, and the README's API reference link doesn't resolve.

## Releasing

Releases go out from `.github/workflows/release.yml`, which runs only when
dispatched by hand. A run with `publish` unchecked (the default) restores,
checks formatting and generated code, builds, runs the unit, README and
contract tests, packs, and keeps the `.nupkg` and `.snupkg` as the `nupkg`
artifact. It publishes nothing. With `publish` checked, a second job in the
`nuget` environment pushes exactly those files to NuGet.org through trusted
publishing: `NuGet/login` exchanges the job's OIDC token for a short-lived
API key, so no NuGet key is stored in the repository.

`src/TeachMeHipaa/TeachMeHipaa.csproj` sets `<PublishGuard>true</PublishGuard>`
until launch. The verify job reads it from the project it packed, and the
publish job fails before logging in to NuGet unless it is `false`, so a
`publish` run dispatched by mistake publishes nothing. This is the .NET stand-in for npm's
`"private": true`, which NuGet has no equivalent of.

To ship (Nick):

1. On NuGet.org, sign in as the account that will own `TeachMeHipaa`, and
   under **Trusted Publishing** add a policy: owner `TeachMeHIPAA`,
   repository `teachmehipaa-dotnet`, workflow `release.yml`, environment
   `nuget`.
2. In GitHub, create the `nuget` environment under Settings > Environments,
   with yourself as a required reviewer, and add a `NUGET_USER` secret to it
   holding that NuGet.org user name (the profile name, not an email).
3. In one PR: set `<PublishGuard>false</PublishGuard>` and
   `<Version>1.0.0</Version>` in `src/TeachMeHipaa/TeachMeHipaa.csproj`, move
   the CHANGELOG's Unreleased entry under that version with the date, and
   update the pre-release notes and install commands in the README,
   `docs/guides/getting-started.md` and `docs/docfx/index.md`, and the
   project references in `examples/`.
4. After it merges, dispatch **Release** on `main` once without `publish`
   and inspect the `nupkg` artifact, then again with `publish` checked and
   approve the `nuget` deployment.
5. Tag the release commit `v<version>` and create a GitHub release from the
   CHANGELOG entry.
